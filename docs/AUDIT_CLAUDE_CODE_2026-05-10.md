## TL;DR (for the founder, before the long form)

Six commits since the May-9 audit moved a real amount of stone. **What is now real** that wasn't before: a FastMCP server with 12 tools, hash-chained receipts that actually persist, agent passports with verified bearer tokens and kill switches, a watchdog with six rule-based detectors that read the real graph, a skills CRUD + runner that hits real LLM provider APIs through a Fernet-encrypted vault, and a router-driven multi-page studio. The May-9 audit's verdict — "every byte of decision, signature, merkle root is randomly generated" — is **no longer fully true**. Roughly half of it has been retired.

**What still isn't true at HEAD a013129:**

1. **The post-quantum signing claim is structurally false.** `pqcrypto` is in `pyproject.toml:7` but never imported anywhere in `src/axiom/`. The string `"ml_dsa_65"` appears in `src/axiom/govern/ledger.py:7` as a label rotated by `SIGNING_SCHEMES[index % 3]`. The `signature` column on the `receipts` table is variously: `merkle_root` (a SHA-256 of `f"root:{index//10}:{receipt_id}"`), `uuid4().hex`, or `f"demo-watchdog:{alert.alert_id}"`. **There is no Ed25519 keypair, no ML-DSA-65 keypair, no verify function that does crypto.** The receipts in the DB right now have `signing_scheme` of `ed25519`, `ml_dsa_65`, `hybrid` rotated by modulo — but the bytes underneath are SHA-256 of metadata strings.
2. **There is no Merkle tree.** What exists is a linked hash chain: each `Receipt` row has `prev_hash` and `this_hash`, where `this_hash = SHA-256(canonical_payload_without_this_hash)` (`src/axiom/govern/receipts.py:120-126`). This is a chained Merkle leaf with no tree above it. The roadmap promises RFC 6962 with Signed Tree Heads. Neither the tree nor the STH exists.
3. **The four-mode policy claim is two-modes-and-a-string.** `ALLOW` and `DENY` are real and enforced. `CORRECT` is real *only* when four narrow conditions coincide (`vault_unlocked` env var + entity composite_importance ≥ 0.45 + intent in a four-element risky set + entity actually found). `PAUSE` appears once in the codebase as a string literal in `src/axiom/policy/interfaces.py:7` and is **never produced by any code path**.
4. **`policies/intelligent.yaml` is dead.** It is the only YAML in `policies/`. No `yaml.load` anywhere in `src/`. The policy decision is `random.random() < deny_rate` (`src/axiom/govern/policy_evaluator.py:84`), with `policy_id = f"AEGIS-{(self._reason_index % 9) + 1}"`. The Phase 0 design specified ordered first-match-wins clauses. None of that exists.
5. **`/api/sources` is still synthetic.** `src/axiom/studio/sources.py:30` returns Slack/Linear/GitHub/Notion/Email/Meetings rows where `count = baseline + entity_count * (index+1)`. There are zero real connectors in `src/axiom/sources/` — only `synthetic.py` (fixture loader), `live_synthetic.py` (timer-driven event generator), `event_generators.py` (canned title pools), and `base.py`. The `sources` table in `axiom.db` has zero rows.
6. **The skills file claim has a subtle shape problem.** Skills exist as JSON rows with prompt templates registered by humans and executed against real LLMs. They are **not** what Tom's RFS asks for: "an executable skills file for AI" emitted by walking Process entities. The `SkillsEmitter` ABC in `src/axiom/skills/interfaces.py:19` still raises `NotImplementedError`. No `SKILL.md` files exist. No code walks Process entities to compile skills.
7. **The receipts are persisted but marked `demo_flag=True` at 17 different call sites.** Every receipt produced via `_persist_policy_receipt`, every watchdog receipt, every demo-action receipt, every snapshot receipt — `demo_flag=True`. The single path that sets `demo_flag=False` is `axiom.skills.runner._run_skill_with_session` (line 211) for successful skill runs.
8. **The DB confirms the asymmetry.** `axiom.db` has 5,829 entities, 26,536 edges, 6 receipts. Of those 26,536 edges, **23,223 (87.5%) are `same_cluster_related`** — auto-generated by `EdgeProposer` to fill in within-cluster pairs. They look like relationships in the UI; they encode only "two entities share a cluster bucket". This ratio is *worse* than at 2a220a1 (81%).

The four "load-bearing differentiators" — post-quantum signing, Merkle anchoring, three-mode policy with CORRECT, executable skills — exist as **scaffolds with surface ergonomics and demo-grade fillings**. The plumbing is real; the substance is not. The shape of a regulator-grade trust system is visible. The bytes inside it are not regulator-grade.

The honest pitch is in §10.

## 1. The four pillars — claimed vs actual

### Pillar 1 — Graph-native pre-execution governance

**What DESIGN.md says it should be.**

> "AXIOM governance is the runtime policy+signing layer enforcing ALLOW/CORRECT/DENY (plus PAUSE when uncertain) and emitting verifiable receipts for every agent action." (`DESIGN.md` §1, line 14)

The phase 9 spec elaborates: ordered first-match-wins YAML clauses, retry budget per `task_id`, cosine drift detection between adjacent action payloads, three response shapes that change agent behavior, escalation to a human approval queue.

**What the code actually does.**

Pre-execution gating exists and is wired into the MCP tool surface. `src/axiom/mcp/server.py:346-394` (`_enforce_preflight`) runs before every mutating tool call (record_action, register_skill, run_skill, archive_skill, request_human_approval). It calls `_policy_preflight` (line 263) which: (a) fetches the target entity's cluster + composite_importance + a suggested-alternative neighbor from a cached graph, (b) verifies the bearer token against `agent_passports` + scope, (c) calls `DemoPolicyEvaluator.evaluate`.

The evaluator (`src/axiom/govern/policy_evaluator.py`) is **not policy in any sense the design doc means**:

- **CORRECT** is produced only when `entity_importance >= 0.45 AND intent in {delete, modify_policy, approve_exception, force_push} AND vault_unlocked AND target_entity_id is set` (lines 65-81). Guidance text cycles through four hardcoded templates (`CORRECT_GUIDANCE_TEMPLATES`, line 20). `policy_id = f"AEGIS-C{(i % 9) + 1}"`.
- **DENY** is produced when `cluster_id == "billing_payments" AND intent == "write"` *or* `random.random() < deny_rate` (default 0.15) (line 84). Reasons cycle through four hardcoded strings (`DENY_REASONS`, line 7). `policy_id = f"AEGIS-{(i % 9) + 1}"`.
- **ALLOW** is the fallthrough.

Drift detection (DESIGN §7.2: "compute cosine similarity between successive action payload embeddings within a `task_id`; if below `drift_threshold_cosine`, escalate") is **not implemented**. `policies/intelligent.yaml` exists, contains a single `clause_000` matching `tool: "*"` decision `allow`, and **is never parsed by any code in `src/`**.

There is *one* signal of graph-nativeness: the preflight uses the target entity's `composite_importance` (a real PageRank-style score from `OrganizerAgent`) and picks a real neighbor as `suggested_alternative` (`mcp/server.py:407-428`). So at least the policy is **looking at** the graph before deciding — but it then ignores what it sees and rolls a die.

**Score: 4/10.** The wiring is real (preflight is on the hot path; passports gate scope; receipts persist). The decision underneath is a deny-rate + a four-condition correct path + a label-rotating policy_id. Calling this "policy enforcement" is generous; calling it "graph-native" is a stretch.

**The one graph-native thing that does work.** `_entity_context` (mcp/server.py:407-428) picks `suggested_alternative` by walking the entity's outgoing+incoming edges, materializing the neighbor's `composite_importance`, and returning the highest-ranked one as a CORRECT alternative. That is a real traversal of the real graph. The rest of the decision logic ignores everything `_entity_context` returns except importance ≥ 0.45.

**What's missing structurally.** No clause set is loaded at startup. There is no `PolicyLoader`, no `policies/` directory scanner, no `yaml.safe_load`. Phase 0 §7.1 specified an ordered clause list with `match` predicates over `(tool, action_type, target_type, field)` — none of these dimensions are matched in code. `task_id` is part of the spec'd request envelope (DESIGN §6.2 `axiom_record_action`) and is **not threaded through** any of the MCP tools registered in `build_mcp_server`. So even if `policies/intelligent.yaml` were loaded, there is no `task_id` to scope retry budget against.

### Pillar 2 — Post-quantum cryptographic receipts (ML-DSA-65)

**What DESIGN.md says it should be.**

> "Every action post-quantum signed (ML-DSA-65) and Merkle-anchored (RFC 6962). … Hybrid signing: Ed25519 (fast) + ML-DSA-65 (post-quantum) on every action." (`docs/ROADMAP.md` lines 32, 277-278; `DESIGN.md` §4.1 explicitly: `signing_scheme: "ed25519+ml-dsa-65"`, `signature_ed25519: base64`, `signature_mldsa: base64`.)

Founder ruling Q4: "**`pqcrypto` package (NIST FIPS 204 reference implementation, audited). No alternatives.** Audited reference implementation is the only correct choice for crypto. Roll-your-own is non-negotiable malpractice."

**What the code actually does.**

```
$ grep -rn "ed25519\|mldsa\|ml_dsa\|pqcrypto" src/axiom/
src/axiom/sign/interfaces.py:7:     SigningScheme = Literal["ed25519+ml-dsa-65"]   # type label only
src/axiom/sign/interfaces.py:14-15: signature_ed25519_b64: str / signature_mldsa_b64: str   # dataclass fields
src/axiom/sign/interfaces.py:27,31: raise NotImplementedError("Signer.sign is stubbed; lands in Phase 10")
src/axiom/govern/ledger.py:7:       SIGNING_SCHEMES = ("ed25519", "ml_dsa_65", "hybrid")   # rotating string label
src/axiom/govern/passports.py:19:   VALID_SIGNING_SCHEMES = {"demo", "ed25519", "hybrid"}
```

`pqcrypto` is in `pyproject.toml:7` and **never imported anywhere in `src/`**. The `cryptography` package is imported only in `vault/crypto.py` and `govern/llm_keys.py` — exclusively for **Fernet** (symmetric AES-128-CBC + HMAC-SHA256), not asymmetric signing.

The actual signature production:

- `demo_receipt(...)` (`src/axiom/govern/ledger.py:10-31`): `receipt_id = sha256(f"{action_id}:{decision}:{agent_name}:{index}")`, `merkle_root = sha256(f"root:{index//10}:{receipt_id}")`, `signing_scheme = ("ed25519", "ml_dsa_65", "hybrid")[index % 3]`. Returns a dict with `"demo": True`.
- `chain_insert_receipt` (`src/axiom/govern/receipts.py:160-181`) stores `signature = str(receipt_seed.get("signature") or receipt_seed["merkle_root"])` — i.e., the `merkle_root` SHA-256 string is shoved into the `signature` column.
- Watchdog (`src/axiom/govern/watchdog.py:346`): `signature=f"demo-watchdog:{alert.alert_id}"`.
- Skill runner success path (`src/axiom/skills/runner.py:209`): `signature=uuid4().hex`.
- Passport "signature" (`src/axiom/govern/passports.py:67-73`): `_demo_signature(row) = sha256(f"axiom-demo-passport:{canonical_json(row)}")`.

The receipt rows in the live DB confirm this:

```
$ sqlite3 axiom.db "SELECT signing_scheme, signature, demo_flag FROM receipts"
ml_dsa_65 | 388b94258814...    | 1
hybrid    | faac384d9f1b...    | 1
ed25519   | 87ff882c953b...    | 1
ml_dsa_65 | 092740b72fbf...    | 1
hybrid    | e316dbd5c17c...    | 1
ed25519   | 17a5111765b3...    | 1
```

Six rows, all `agent_name=smoke_agent`, all `intent=read`, all `decision=allow`, all `demo_flag=1`, signing scheme rotating by index modulo 3. The `signature` column is 64 hex chars in each row — every one of them a SHA-256 of metadata strings, not a real cryptographic signature.

**Score: 0/10.** The signing pillar is a label-rotation system over hash digests. There is no Ed25519 keypair file, no ML-DSA-65 keypair, no verify path that does cryptographic verification, no signature that any third party could verify with a public key. The founder ruling specifically forbade roll-your-own. The current state is *worse* than roll-your-own — it's roll-nothing-and-call-it-signed.

**The "verify" endpoint is a chain-walk, not a signature verify.** `/api/internal/receipts/{receipt_id}` (`studio/server.py:1284-1297`) calls `verify_receipt_chain`, which iterates every receipt in time order and confirms `prev_hash` links + recomputes `this_hash`. If the chain is intact, it returns `"verified"`. **No public key is consulted.** A third party with a copy of the JSON could re-derive `this_hash` themselves; this is a tamper-evidence property of any append-only ledger, not a signature property. A regulator asking "who attests this happened?" gets no answer.

**Why this matters more than the May-9 audit said.** The README at HEAD a013129 explicitly says "no cryptographic signing of agent actions" in its honest disclaimer paragraph. The pitch material (per CEO context for this audit) says "post-quantum signed actions" and "regulator-grade trust." The repo has *two truthful documents internally* (README, AXIOM_AUDIT_REPORT) and *one aspirational claim externally* (pitch, ROADMAP §1, DESIGN §1). At YC submission, the external claim is what gets evaluated. The internal documents will look like an admission against interest.

### Pillar 3 — Merkle ledger

**What DESIGN.md says it should be.**

> "RFC 6962 Certificate Transparency log structure. Checkpoints emitted every 1000 leaves OR every hour, whichever first. Each checkpoint produces a Signed Tree Head (STH). Inclusion proofs computed on demand via `axiom_verify_receipt(receipt_id)`." (Founder ruling Q3, `DESIGN.md` Appendix A.)

DESIGN §4.1: `merkle_leaf_index: int` is part of every action receipt; `axiom_verify_receipt` returns `verified: bool, details: dict` with inclusion proof.

**What the code actually does.**

A linked hash chain. `src/axiom/govern/receipts.py:128-200` (`chain_insert_receipt`):

```python
previous = session.execute(
    select(Receipt).order_by(desc(Receipt.created_at), desc(Receipt.id)).limit(1)
).scalar_one_or_none()
...
receipt = Receipt(
    ...
    prev_hash = previous.this_hash if previous is not None else None,
    this_hash = "",
    ...
)
receipt.this_hash = compute_receipt_hash(receipt)   # sha256(canonical_payload_minus_this_hash)
```

And `verify_receipt_chain` (line 203):

```python
for row in rows:
    if row.prev_hash != previous_hash: return "broken"
    if compute_receipt_hash(row) != row.this_hash: return "broken"
    previous_hash = row.this_hash
    if row.id == receipt_id: return "verified"
```

This is a **single-linked hash chain**, not a Merkle tree. There is:
- No tree (no internal nodes, no `compute_tree(leaves) -> root`).
- No `merkle_leaf_index` column on the `Receipt` model anywhere — the column was dropped during the migration to the new `chain_insert_receipt` shape (the `ensure_receipts_schema` migration drops `ix_receipts_merkle_leaf_index` if it survives from a legacy table — `receipts.py:81`).
- No Signed Tree Heads, no checkpoints emitted, no `axiom_anchor_checkpoint`, no `/api/internal/merkle-checkpoints` endpoint.
- No inclusion proof. The "verify" endpoint walks the linear chain end-to-end and returns "verified" / "broken".
- `/api/internal/merkle-status` (`studio/server.py:1299-1326`) returns `chain_length`, `head_hash`, `tail_hash`, and a per-`signing_scheme` count — **`signing_schemes_distribution = {"ed25519": 0, "ml_dsa_65": 0, "hybrid": 0}`** that gets populated by reading the label-rotation column. It cosplays as a Merkle status endpoint.

**Score: 2/10.** A linked hash chain is a real cryptographic primitive — tamper-evident if you keep an external head copy. But it is not the Merkle tree the design promised, and the `merkle_root` field stored on every receipt is a SHA-256 of `f"root:{index//10}:{receipt_id}"`, not a tree root. The two points are for the chain integrity check actually working — `verify_receipt_chain` will catch tampering of any past row.

**Why the "Merkle" naming is more than cosmetic.** In a Merkle tree, an auditor can verify a single receipt's membership in the log with `O(log N)` hashes — the inclusion proof — without reading the whole chain. RFC 6962 is the design point. The current chain-walk is `O(N)`, which means: at 1M receipts, every audit-verify is a million-row table scan. Worse, there is no `Signed Tree Head` to commit-to externally: a malicious operator who controls the DB can rewrite the entire chain and recompute every `this_hash` and `prev_hash` (the `compute_receipt_hash` function is deterministic and runs on any row). Without an external anchor — an STH signed under a private key the operator doesn't control, or a public log like CT — the chain has only **internal** tamper-evidence, not **external** non-repudiation. The roadmap's regulator-grade framing requires the latter.

**One thing that's better than the May-9 audit gave it credit for.** The `chain_insert_receipt` function uses `BEGIN IMMEDIATE` on SQLite (`receipts.py:139`) to serialize chain appends, so concurrent inserts cannot fork the chain. The deduplication by `action_id` (line 145) prevents replay. The `created_at` adjustment to avoid timestamp collisions (line 157) prevents ordering ambiguity. These are real correctness choices that show someone understood what a hash chain needs to be correct under concurrency — the implementer knew what they were doing, they just stopped one design-fidelity step short of a tree.

## 2. The agent runtime gap

The system claims to enable AI agents to act safely against company knowledge. The five-step trace:

### (a) Authenticate via passport — **YES**

Code path:
- `src/axiom/govern/passports.py:225-251` (`verify_passport`): SHA-256 of bearer token is looked up in `passport_credentials`; if present, the joined `agent_passport` row is validated (`_validate_passport`, line 209) for: signing scheme, `not_before`, `expires_at`, `revoked_at`, `kill_switch`. On success, `presented_count` is incremented and the row is cached in `_VERIFY_CACHE` for 60s.
- `src/axiom/mcp/server.py:193-215` (`_resolve_passport` / `_require_passport_scope`): called at the top of every MCP tool. Without a token, falls back to `ensure_system_passport` which auto-issues a `demo_passport` with `*` scope and 1-year TTL (`passports.py:187-206`). So an external agent calling without auth gets the system passport.

Real plumbing. The signing scheme is `"demo"` (`passports.py:144`) and the "signature" is SHA-256 of the canonical payload, but the lifecycle (issue → present → verify → scope → revoke → kill-switch) is wired through, and the `PassportsPage.tsx` UI uses it for the full CRUD loop.

**One gap**: the `ensure_system_passport` fallback means MCP tools work without a passport token — the auth is permissive by default, with the system passport granting `*` scope.

### (b) Discover skills — **YES**

- `src/axiom/mcp/server.py:1258-1273` (`axiom_list_skills` MCP tool): wraps `list_skills_with_session` from `skills/registry.py:176`. Real query against the `skills` SQLAlchemy table with `status` and `intent` filters.
- The same logic is exposed over HTTP at `/api/internal/skills` (`studio/server.py:887`).

**But**: the `skills` table in the live DB has **zero rows**. No skills exist for an agent to discover. Phase 13.b added the registration UI; nothing seeds skills from Process entities. The `SkillsEmitter` ABC remains unimplemented (`skills/interfaces.py:19-26`, both methods raise `NotImplementedError`).

### (c) Execute a skill — **YES**

- `src/axiom/mcp/server.py:1287-1302` (`axiom_run_skill`).
- `src/axiom/skills/runner.py:_run_skill_with_session` (line 140): renders the prompt template via `string.Formatter`, fetches the LLM provider key from the Fernet-encrypted `llm_provider_keys` table (`vault/crypto.py` + `govern/llm_keys.py:176-181`), POSTs to Anthropic/OpenAI/Groq/Mistral, parses the response, validates against `output_schema`, persists a `SkillRun` row, chains a `Receipt` row.

**Real LLM execution path**. Provider keys are vault-encrypted with Fernet; the master key falls back to a self-generated `.axiom_vault_key` file at first run (`llm_keys.py:70-88`) — usable in dev, weak in production unless `AXIOM_VAULT_KEY` is set in the env.

**But**: validation of the LLM output (`_validate_schema`, runner.py:107) is shallow — it only enforces presence of `required` keys and primitive `type`. No JSON Schema validator. No retry on bad output. No idempotency on the LLM side.

### (d) Action gated — **PARTIAL**

- `mcp/server.py:346-394` (`_enforce_preflight`) runs at the head of `record_action`, `register_skill`, `run_skill`, `archive_skill`, `request_human_approval`.
- On `correct`: returns `{decision: "correct", guidance, suggested_alternative}` and short-circuits the action (`mcp/server.py:704-716, 756-764`). The agent sees guidance and must retry.
- On `deny`: raises `ToolError` (`mcp/server.py:393, 496`). The action is blocked.

The gate is **structurally real** (the code that would make the decision is on the hot path), but the **decision body is RNG**: `random.random() < deny_rate` (policy_evaluator.py:84) plus four CORRECT-condition gates. The phase-9 promise — ordered first-match-wins YAML clauses, drift detection between adjacent payloads in a `task_id`, retry-budget exhaustion that escalates to human approval — does not exist. `task_id` is never threaded through the preflight. There is no retry budget. There is no drift detection.

### (e) Signed receipt — **PARTIAL (the bytes are fake)**

- `mcp/server.py:221-261` (`_persist_policy_receipt`): for every gated outcome, a `Receipt` row is inserted via `chain_insert_receipt`. The receipt has `signing_scheme` (rotating label), `signature` (SHA-256 hex string of `root:{index//10}:{receipt_id}`), `prev_hash` and `this_hash` (real SHA-256 chain). `demo_flag=True` is set at every call site (line 480, 589, 659, 775).
- Every receipt is also emitted as a `receipt_added` WebSocket envelope (`mcp/server.py:337-343`).
- A successful skill run sets `demo_flag=False` (`skills/runner.py:211`) — this is the **one** path that claims a non-demo receipt. Its signature is `uuid4().hex`.

The shape works end-to-end: receipt persists, has a verifiable chain position, hits a WebSocket. The bytes underneath are not a signature in the cryptographic sense.

**Verdict: 5 of 5 paths exist; 3 of 5 are real-by-bytes.** Auth (a) and discovery (b) are real. Execution (c) is real for skills that exist. Gating (d) is structurally real but RNG-driven. Receipt (e) is persisted but unsigned in the cryptographic sense.

### 2.1 Concrete trace: external agent invokes an MCP tool

A request from outside enters at `serve_stdio` (`mcp/server.py:1341`), which runs the FastMCP server on stdio. Take `axiom_run_skill(skill_id, input_payload, idempotency_key, passport_token)` as the canonical mutating call:

1. **Tool entry** (`mcp/server.py:1287-1302`) — the wrapped function calls `service.run_skill(...)`.
2. **Idempotency check** (`mcp/server.py:684-688`) — `(skill_runner, idempotency_key)` key looked up; if present and unexpired (TTL 3600s), the cached response is returned immediately. Real, works.
3. **Skill load** (line 691) — `get_skill_with_session(session, skill_id)` raises `SkillNotFound` (caught by the wrapper, re-raised as `ToolError`).
4. **Preflight** (line 694) — `_enforce_preflight(agent_name="external_mcp_client", intent=f"skill:{skill_name}", target_entity_id=None, ...)`. Note: `agent_name` is hardcoded to `"external_mcp_client"` for every external call. There is no way for the agent to identify itself by name — passport identifies the *holder*, but the receipted `agent_name` is generic.
5. **Passport scope** — `_require_passport_scope(intent="invoke_skill", cluster_id="external_mcp", skill_id=skill_id)` — scope intent is `"invoke_skill"` (not the user-supplied `intent`). If passport has `*` in `scope_skills` and `*` in `scope_intents`, allowed.
6. **Policy** — `DemoPolicyEvaluator.evaluate("external_mcp", f"skill:{skill_name}", entity_importance=None, ...)`. Because `entity_importance=None`, the CORRECT path can't fire. So the decision is ALLOW (~85%) or DENY (~15%).
7. **On CORRECT** (cannot happen due to importance=None, but theoretically) — return guidance dict, cache in idempotency, return early. No skill execution.
8. **On DENY** — persist receipt, raise `ToolError`. No skill execution.
9. **On ALLOW** — call `run_skill(skill_id, input_payload, "external_mcp_client", session_factory, event_callback=emit, receipt_policy_id, receipt_reason, receipt_passport_id)`.
10. **Skill execution** (`skills/runner.py:140-244`) — creates `SkillRun(status="running")`, emits `skill_run_started`. Then re-opens session, fetches the API key from vault, renders prompt, POSTs to provider with a 30s timeout, parses response, validates schema, persists `SkillRun(status="success", output_payload)`, chains a Receipt. Emits `skill_run_completed`. Returns `{run: ..., skill: ...}`.
11. **Error handling** — if any exception during execution, the `SkillRun` is updated with `status="failed"` and `error_message`. No receipt is chained for failures — only successful runs produce receipts.

**Observations from this trace:**

- The external agent's *identity* is `"external_mcp_client"` in every persisted row. The passport identifies the *credential*, but the receipted agent_name is uniform. An auditor looking at the receipts table cannot distinguish between two external agents sharing different passports.
- The skill-run policy gate cannot CORRECT because `target_entity_id=None` for skill runs (line 698). So skill runs always either ALLOW or DENY at the 15% rate. The "intent + importance" CORRECT path is unreachable.
- Failed skill runs leave a `SkillRun(status="failed")` row but no Receipt. The receipt chain doesn't witness failures. That's an audit gap: a regulator asking "did this agent attempt this action?" only gets a yes from successes.
- The vault key fallback (`govern/llm_keys.py:70-88`): if `AXIOM_VAULT_KEY` is unset, the runner *generates a key and writes it to `.axiom_vault_key`*. This is the "dev convenience" path. In production, this means a first-run on a fresh container creates a key that no one knows; subsequent restarts can decrypt; but if the container is replaced, the key is lost and all encrypted secrets are unreadable. The key file mode is `0o600` (line 79) so it's user-only, but it's still on the local FS in cleartext.

### 2.2 Where the runtime is honest

It is worth flagging: the runtime *does not silently fake auth*. The `system_passport` fallback is documented in code (line 197 of passports.py is a comment-less but readable function), and the system passport row in the DB has the literal name `demo_system_agent`. The fact that unauthenticated calls succeed is a *permissive default*, not a hidden bypass. A YC reviewer who reads the code sees this in 30 seconds — same as the May-9 audit saw the receipt fake — but it's at least labeled.

## 3. The governance loop

ALLOW / CORRECT / DENY / PAUSE — the load-bearing claim. Per-mode reality:

### ALLOW

- **Where:** `DemoPolicyEvaluator.evaluate` fallthrough (`policy_evaluator.py:88`); MCP `_enforce_preflight` returns through without raising (`mcp/server.py:369-370`).
- **What triggers it:** Anything not in the CORRECT path (importance ≥ 0.45 + risky intent + vault unlocked) and not in DENY (`cluster_id == "billing_payments" AND intent == "write"` or `random.random() < deny_rate`). Default `deny_rate = 0.15` — so ~85% of demo-simulator actions allow.
- **What enforces it:** Action proceeds (`record_action` persists, broadcasts `agent_action`/`agent_action_evaluated`/`receipt_added`). Receipt is chained.

**Real, enforced.**

### CORRECT

- **Where:** `DemoPolicyEvaluator.evaluate` lines 65-81. MCP short-circuit returns at `mcp/server.py:562-571, 629-637, 704-716, 756-764` — any tool that gets CORRECT returns the guidance dict and does *not* perform the action.
- **What triggers it:** All four must hold: `entity_importance >= 0.45`, `intent in {"delete", "modify_policy", "approve_exception", "force_push"}`, `vault_unlocked == True`, and the target entity must be resolvable. Guidance string cycles through four hardcoded templates (`CORRECT_GUIDANCE_TEMPLATES`).
- **What enforces it:** The MCP tool returns `{decision: "correct", guidance, suggested_alternative}` instead of performing the action. The receipt is persisted with `decision = "correct"`. A `agent_action_corrected` envelope is broadcast.

**Real, enforced, but narrow.** Three of the four trigger conditions are environmental, not intrinsic to the action. If the demo simulator isn't running, if `AXIOM_VAULT_KEY` is unset, or if the intent isn't in the four-element set, CORRECT will never fire. The phase-9 promise of retry-budget tracking, drift detection, and 3-CORRECTs-equals-auto-DENY-with-escalation is absent.

### DENY

- **Where:** `DemoPolicyEvaluator.evaluate` lines 83-87; MCP raises `ToolError` at `mcp/server.py:393, 496`.
- **What triggers it:** `cluster_id == "billing_payments" AND intent == "write"` (hardcoded "billing is sacred" rule), or `random.random() < deny_rate`. Reason cycles through four hardcoded strings. `policy_id = f"AEGIS-{(i % 9) + 1}"`.
- **What enforces it:** The MCP tool raises an error (caller sees a ToolError); the receipt is persisted with `decision = "deny"`; `agent_action_blocked` is broadcast.

**Real, enforced**, with the same caveat that the *reason* it denies is RNG plus one billing-themed hardcode.

### PAUSE

- **Where:** The string `"pause"` appears in:
  - `src/axiom/policy/interfaces.py:7` — `PolicyDecision = Literal["allow", "correct", "deny", "pause"]` — typed but unused.
  - DESIGN.md §6.2 lists `axiom_pause_for_evidence` as a required MCP tool.
  - `docs/AXIOM_PHASE_5_12_SPEC.md` and README list PAUSE as a fourth mode.
- **What triggers it:** Nothing. There is no code path in `src/axiom/` that produces `decision = "pause"`. `axiom_pause_for_evidence` is **not registered** in `build_mcp_server` (`mcp/server.py:1142+`).
- **What enforces it:** N/A. The PolicyDecision type accepts it; no one ever returns it.

**Not implemented. Pure label.** Founder ruling Q6 deferred Calibra to Phase 7 and Calibra is what would have produced UNCERTAIN states for PAUSE to trigger on. The deferral is documented; the PAUSE claim in pitch material is not.

### What an external agent actually experiences

End-to-end: an external agent issues `axiom_record_action(agent_name="claude", intent="write", target_entity_id="ent_X", proposed_action="modify_policy")` against the MCP server. The path:

1. `_resolve_passport` (mcp/server.py:193) — without a `passport_token`, falls back to `ensure_system_passport` which returns the demo system passport with `*` scope. So unauthenticated calls succeed.
2. `_entity_context(ent_X)` — fetches cluster, importance, suggested-alt from cache.
3. `_require_passport_scope` — system passport has `*`, succeeds.
4. `DemoPolicyEvaluator.evaluate(cluster, "write", importance=I)` — if `cluster == "billing_payments"` and `intent == "write"`: DENY. Otherwise: roll `random.random() < 0.15` for DENY; if importance ≥ 0.45 AND intent in risky AND vault unlocked: CORRECT; else ALLOW.
5. If ALLOW: receipt persisted with `decision=allow`, broadcast envelope, return `{action_id, decision: "allow", receipt_id, signing_scheme: "ml_dsa_65" | "ed25519" | "hybrid", reason: "policy checks passed", policy_id: "AEGIS-1", passport_id: "demo_passport", demo: true}`.
6. If CORRECT: receipt persisted with `decision=correct`, return guidance dict. The action does not perform.
7. If DENY: receipt persisted with `decision=deny`, MCP raises `ToolError` with `reason (policy_id=AEGIS-N)`.

**The agent always gets a receipt back**, signed with one of three label-rotated scheme names. The receipt ID is a hex string. The signature is a hex string. The merkle_root is a hex string. All of these look right. None of them are real signatures.

## 4. The skills file (Tom's "executable skills file")

Tom's RFS (verbatim, ROADMAP.md Appendix A, line 537): *"A system that pulls knowledge out of all these fragmented sources, structures it, keeps it current, and turns it into an executable skills file for AI."*

DESIGN.md §8: Skills emit as **signed `SKILL.md` files with YAML front-matter** (id, version, scope, inputs, outputs, side_effects, requires_approval, calibra_threshold, signing scheme + signature, provenance.emitted_from = process entity id). The emitter walks Process entities and produces one skill per process.

The four sub-claims:

### (a) Skills must be machine-readable — **YES**

`Skill` SQLAlchemy model has structured fields: `name`, `description`, `intent` (enum: classify/summarize/extract/transform/monitor), `prompt_template`, `output_schema` (JSON), `llm_provider`, `llm_model`, `trigger_type` (manual/schedule/event), `trigger_config` (JSON), `status` (draft/active/paused/archived). Returned as JSON via `skill_to_dict` (`skills/registry.py:46`) over both HTTP (`/api/internal/skills`) and MCP (`axiom_get_skill`).

### (b) Skills must be discoverable by external agents — **YES**

`axiom_list_skills` MCP tool (`mcp/server.py:1258-1273`) wraps `list_skills_with_session`. Optional filters: `status`, `intent`. External agent calls `mcp.tool("axiom_list_skills")` and gets back a JSON list.

But: **zero rows** in the `skills` table in the inspected DB. No bootstrap seeding from Process entities. An external agent calling discovery on a fresh deployment will find nothing until someone uses the registration UI.

### (c) Skills must be executable — **PARTIAL**

Yes, the registered skills are executable: `axiom_run_skill` → `_run_skill_with_session` → real HTTP POST to LLM provider with the prompt template rendered against the input payload. Output is parsed, optionally schema-validated, returned, persisted in `skill_runs`, receipted.

**But this is NOT what Tom's RFS describes.** Tom's "executable skills file" is the **artifact** that captures *how a company handles refunds*, *how engineers respond to incidents* — i.e., it should be the **compiled output of walking the company's Process entities**. The current implementation is a "prompt-skill registry" where a human types a prompt and points it at a model. The compilation step (Process → SKILL) doesn't exist.

`SkillsEmitter` (`skills/interfaces.py:19`) remains an abstract stub:
```python
@abstractmethod
def emit_all(self) -> list[SkillDescriptor]:
    raise NotImplementedError("SkillsEmitter.emit_all is stubbed; lands in Phase 8")
```

The DB has 120 `process` entities (`SELECT type, COUNT(*) FROM entities GROUP BY type`); none of them have produced a SKILL.md. No filesystem mirror at `~/.axiom/skills/`. No signature sidecar.

### (d) Execution must be auditable — **PARTIAL**

`SkillRun` rows persist with `input_payload`, `output_payload`, `status`, `duration_ms`, `error_message`, `agent_name`, `receipt_id`. The linked Receipt has a hash-chain `this_hash`. The signature column for skill-run receipts is `uuid4().hex` (`skills/runner.py:209`) — a random hex string, not a signature.

So: the *trail* is auditable (every run produces a Receipt; the chain detects tampering). The *signature* is not.

**Composite verdict: PARTIAL on three of four. The artifact-shape claim — `SKILL.md` files compiled from Process entities — is NO.**

Zero have been walked. The fact that `process` has no watchdog rule, no policy clause, no skills emitter, and is not even rendered with distinguishing iconography — despite being the type the executable-skills-file story stands on — is the single biggest "we have not gotten to the actual product yet" signal in the codebase.

For "the company brain agents and humans both navigate" (ROADMAP §1), the human-navigation affordance of "is this a person, a doc, a ticket?" is absent at the visual layer.

**Type-aware search relevance.** `hybrid_search` (`retrieval/search.py`) accepts `entity_types: list[str] | None` as a filter. Without that filter, type uniformly affects nothing. The graph-search component (`graph_search`) walks edges without weighting by either endpoint's type. This is acceptable for v0 but means the system has no concept of "weight people > code for ownership queries."

## 7. Demo-fragility under a real workload

If 10,000 real entities arrived tomorrow, ranked by what breaks first:

### 7.1 `/api/entities` and `/api/edges` dump entire tables (server.py:977, 1039)

```python
@app.get("/api/entities")
def get_entities() -> list[dict[str, Any]]:
    with session_local() as session:
        rows = session.execute(select(Entity)).scalars().all()
        return [EntityDTO.model_validate(r).model_dump(mode="json") for r in rows]

No pagination, no filtering, no projection. Brain.tsx bootstrap fetches both on page load (already ~12 MB JSON at 5,829 entities + 26,536 edges; ~30+ MB at 10,000 entities + EdgeProposer's quadratic blowup). Every reload re-fetches everything.

**Failure mode:** browser tab OOMs at ~50K entities; API rate-spikes on every page open; WebSocket replay is fine but the initial REST bootstrap is the bottleneck.

**Fix:** add `?limit` + `?since=updated_at` pagination, or send entities over the WebSocket and let bootstrap be a snapshot.

### 7.2 EdgeProposer quadratic blowup

`src/axiom/organize/edge_proposer.py` proposes within-cluster edges every 15s. At 10K real entities clustered into 7 buckets (~1,500 each), the saturating edge count per cluster is ~1.1M. Even with deduplication and rate-limiting, the `edges` table will balloon. The frontend then has to render this in Three.js.

**Failure mode:** Three.js scene degrades below 30 FPS, then 15, then crashes; `/api/edges` payload grows to 100+ MB; SQLite `edges` index pressure becomes the bottleneck for ingest.

**Fix:** make `same_cluster_related` derivation runtime-only (don't materialize), or cap to N edges per entity, or remove entirely (it encodes nothing).

    cur.executemany("INSERT INTO entities_fts(entity_id, searchable) VALUES (?, ?)", rows)
```

Every MCP service start (and on cache miss after restart) loads the entire graph into a Python dict and rebuilds an FTS5 index in an in-memory SQLite. At 10K + 1M edges, that's 100+ MB of Python objects per MCP process plus the FTS index. The incremental sync (line 851) handles deltas, but the initial rebuild is unavoidable.

**Failure mode:** MCP processes are heavyweight; spawn time grows linearly with graph; multiple MCP clients each carry their own cache.

**Fix:** push search to Postgres FTS or pgvector + AgentDB once that's a real platform decision; don't keep a per-process in-memory copy of the entire graph.

### 7.5 No real ingestion path exists

This is the silent killer. 10,000 real entities can't arrive because there is **no real connector**. `src/axiom/sources/` contains: `base.py` (Source ABC), `synthetic.py` (fixture loader), `live_synthetic.py` (timer-driven generator), `event_generators.py` (canned pools), `interfaces.py` (typing stubs).

```
$ ls src/axiom/sources/
__init__.py  base.py  event_generators.py  interfaces.py  live_synthetic.py  synthetic.py
```

No `linear.py`, no `slack.py`, no `gmail.py`, no `drive.py`, no `github.py`. Phase 12 (the Linear connector, F5: "Linear is the first real connector") is not started. There is no OAuth flow, no webhook receiver, no entity normalization from any real source.

**Failure mode:** the question is moot. 10K real entities cannot arrive. The runtime fragility points above are unreachable until the ingestion path exists.

### 7.6 Hidden fragilities worth flagging

- **`_full_rebuild` triggers on cache miss every 10 seconds** (`mcp/server.py:143` `_cache_ttl_sec = 10.0`). At 10K entities, that's a 10s-window full-table scan plus a full FTS index rebuild every MCP cache miss. The "incremental sync" path (line 851) only kicks in if `_sync_state.entity_count > 0` and the row counts haven't dropped — i.e., it only catches inserts and edits, not deletes.
- **EventBroadcaster keeps the last 1000 events in-memory** (`ingest/broadcaster.py`). At a real ingest rate of even 10 events/sec, the 1000-event ring buffer is a 100-second window. Browser reconnects after a hiccup longer than 100s lose events. For a "live company brain" with bursty activity, this window is tight.
- **`get_governance` recomputes `policy_entities` with `_is_policy_entity(entity)` for every entity** on every request (server.py:1067-1072). `_is_policy_entity` constructs a haystack string from `entity.type`, `entity.cluster_id`, `data.title`, `data.name`, `data.category`. At 10K entities that's 10K substring searches per /api/governance hit.
- **Watchdog `sweep_once` runs every 300 seconds and reads every entity ID** (`watchdog.py:259-272`). For each entity, it calls `detect_for_entity`, which runs all six rules. R5 (`cluster_outlier`) does a Python-side cosine similarity over peer embeddings every time. At 10K entities × six rules × peer-cosine, the sweep is minutes-long.
- **No connection pool on SQLite.** All API handlers open a `session_local()` per request and close it. Under load, SQLite's single-writer lock will serialize all writes; the watchdog sweep and the ingest pipeline will fight for the lock.

## 8. The pitch gap

CEO pitch (per context): *"Company Brain — executable skills file for AI agents, with regulator-grade trust built in."*

Phrase-by-phrase truthfulness:

### "Company Brain" — **7/10**

Real graph substrate: 7 entity types, typed edges, SQLAlchemy persistence, real-time WebSocket mutation, working 3D visualization, hybrid search (lexical + semantic + graph RRF), PageRank centrality, cluster classification, cluster health monitoring. The May-9 audit was right that this is the strongest part of the build. At HEAD a013129, hybrid retrieval lands (phase 8.6) and the watchdog adds entity-aware rule detection (phase 5.8).

What costs the three points: the brain is populated entirely by synthetic data. No real connector. The "brain of *your* company" claim requires the connector layer that doesn't exist.

### "Executable skills file for AI agents" — **4/10**

Skills exist as JSON rows with prompt templates + provider + model. The `axiom_run_skill` MCP tool executes them against real LLMs. So skills are technically executable.

What costs the six points:
- **Skills are user-typed prompts, not compiled artifacts.** Tom's RFS asks for skills *derived from* a company's processes, decisions, and threads — the "executable skills file" is the *output* of the brain's structuring work. The current implementation is a prompt registry where humans type prompts. The `SkillsEmitter` that would walk Process entities and produce `SKILL.md` files is unimplemented (`skills/interfaces.py:19-26` raises `NotImplementedError`).
- **Skills are JSON rows, not `.md` files.** DESIGN §8 specifies SKILL.md with YAML front-matter and markdown body, mirrored to `~/.axiom/skills/<id>.md` with `.sig` sidecar. None of that exists.
- **Skills are not signed in any cryptographic sense.** Skill-run receipts have `signature=uuid4().hex` (runner.py:209).

### "Regulator-grade trust" — **2/10**

This is where the pitch gap is widest.

Real:
- Receipts persist with a SHA-256 hash chain that detects tampering of past rows.
- Passports have a lifecycle (issue, present, verify, scope, revoke, kill-switch).
- The vault encrypts LLM provider keys with Fernet.

Not real:
- **No cryptographic signing.** `pqcrypto` is declared but unused. `cryptography` is used for symmetric Fernet only. No Ed25519 keypair, no ML-DSA-65 keypair, no asymmetric signing anywhere. The `signature` column on the `receipts` table holds SHA-256 hex strings or UUIDs.
- **No Merkle tree.** The chain is linear; no internal nodes, no STH, no inclusion proof, no checkpoint cadence.
- **No external anchor.** Founder ruling Q3 ("self-hosted is sufficient for launch; external anchoring is a post-launch hardening step") is honored — but the self-hosted version doesn't have STHs either.
- **`demo_flag=True` on every receipt produced by the live MCP path.** A regulator reading the data would see "demo" stamped on every audit row.
- **Policy is RNG.** The policy_id `AEGIS-N` cycles modulo 9. No YAML clause is loaded.

A regulator would need to see (a) public-key-verifiable signatures with key custody and rotation policies, (b) a Merkle tree with inclusion proofs, (c) policy rules expressed declaratively and version-pinned. None of those exist.

### Composite pitch score: **4/10**

The pitch is shaped right. The trust pillar is the load-bearing claim and it's the weakest. If a YC partner clicks into `/api/internal/receipts` or runs `verify_receipt_chain` and then `grep pqcrypto src/`, the pitch unravels in 90 seconds.

3. **Strip every `demo_flag=True` from the MCP record-action path.** Today every receipt the MCP path produces is stamped demo. Even with the synthetic-data substrate, an action taken by a real external agent against the real graph is not, by itself, a "demo action." Distinguish *synthetic data* from *real action against synthetic data*. The `is_demo` indicator should follow the data source, not the action path.

These three fixes do not change the architecture. They make the substance honest enough that the architecture can be the story.
